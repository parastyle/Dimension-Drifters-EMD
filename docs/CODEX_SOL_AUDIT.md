# Codex GPT-5.6-Sol audit — full codebase (2026-07-14)

Four parallel read-only audits run on `gpt-5.6-sol` via Codex CLI 0.144.4: **client render/perf**,
**server sim + netcode**, **data model + codegen pipeline**, and **architecture/tooling**. 70 findings
total (5×P0 · 41×P1 · 24×P2), every one anchored to real file:line references. Raw reports are inlined
below verbatim; this header is the synthesis.

## The five P0s

1. **[DATA] 11 weapons lost their entire authored mechanic block.** The first authoring batch put
   behavior stats in sibling objects (`thrown`/`quake`/`scatter`/`gun` next to `behavior`), which
   `gen-weapon-expansion.mjs` never reads — e.g. Coyote's Grin authored damage 7/range 540/pierce 2,
   ships 4/520/1; Hailshot Hand-Maul authored a 16-damage explosive gun, ships a default 6-damage slug.
2. **[DATA] Supported gameplay fields silently dropped roster-wide** — 71 `muzzleColor`, 8 `bounces`,
   38 source-specific `scalingGrades`, 21 `beam.tickRate`… authored, never emitted. Plus 209 authored
   values silently clamped (75 ranges, 134 swingArcs).
3. **[SERVER] Debug RPCs are production-reachable** — any first-joiner is host, toggles training, and
   `debugSpawn` has no cap: one client can DoS the whole node process.
4. **[CLIENT] Arena restart leaks rooms/listeners/state** — ghost players, stale entity maps, invisible
   enemies, duplicate carousel cards after any restart.
5. **[ARCH] `pnpm start` can't run in production** — it invokes `tsx` (a devDependency); the compiled
   `dist` is never used.

## Cross-cutting themes (what to actually schedule)

- **Silent failure is the house style — make it loud.** Every audit found the same root pattern:
  generators repair/skip/clamp instead of failing (data #3), CI checks 2 of ~8 generated outputs
  (data #6, arch #12), asset manifests aren't validated against files on disk (arch #12), sprite
  installs succeed with a stale atlas (data #9). One `assets:check` + strict-schema pass kills a
  whole class of "lots of assets are missing" bugs — including the ones the user hit in the showroom.
- **One spatial index fixes the server.** Enemy separation O(E²)×2, projectile collision O(P×E),
  AoE/melee full scans — all want the same uniform-grid broad phase (server #2/#3).
- **The alloc-churn twins.** Client ~54k objs/sec at 300 enemies (client #3, server #12) and the
  server's O(E+P) scratch garbage per tick (server #13) are the same fix pattern: ring buffers,
  `sampleInto(out)`, reusable scratch. This was already on our deferred "safe tier" list — now with
  exact line references.
- **Ship less, load less.** No code-splitting, 12.5k-line expansion module in the bundle, ~20 MiB
  blocking arena create(), one monolithic atlas, 82 MiB public tree copied into every deploy
  (arch #2/#3/#4/#5/#6).
- **Trust boundary.** Client-authored belt scrip/upgrades, parry during the invincible level window,
  mystery-loot identity synced pre-reveal, unbounded non-input RPCs (server #7/#10/#15/#11).
- **Availability wants to be a real enum.** `expansion:true` claims "held out" but 173/295 are live
  drops (data #4); banned whips still live in art subjects + sprites (data #13). One
  `fallback|gallery|drop|active|banned` state, everything derived from it.

# Report 1 — CLIENT render/perf
1. **P0 — Arena restart leaves old sockets and global callbacks alive.**  
   Refs: `packages/client/src/scenes/ArenaScene.ts:635`, `:636`, `:638`, `:652`, `:1163-1211`, `:1204`.  
   **Why:** there is no `SHUTDOWN` cleanup for the raw window/canvas listeners, global ScaleManager listener, Colyseus room, state callback, or async retry loop. After a restart, every pointer movement performs multiple `getBoundingClientRect()` calls, old rooms remain joined as ghost players, and old state callbacks can feed `onPatch` using the new room’s session ID.  
   **Fix:** register a named shutdown handler that removes all DOM/scale listeners, stores and invokes Colyseus unsubscribe functions, calls `room.leave()`, clears `room`, and increments a connection-generation token checked after every `await` so abandoned retries cannot install a room.

2. **P0 — The reused ArenaScene retains destroyed GameObject handles and run state.**  
   Refs: `packages/client/src/scenes/ArenaScene.ts:168-223`, `:331-343`, `:384-443`, `:542-580`, `:1373-1379`, `:4145-4147`.  
   **Why:** Phaser reuses the scene instance, but `create()` clears only part of its state. Maps such as `blobs`, `enemies`, `pickups`, `projectiles`, and `zones` still contain objects destroyed by scene shutdown; reconciliation sees `.has(id)` and does not recreate them. `portal`, `rift`, belt objects, UI pools, cooldowns, and event-history maps also survive. `buildCarousel()` appends new cards to the stale array. A restarted scene can therefore have invisible entities, stale portals, duplicate cards, and old combat state.  
   **Fix:** centralize a complete `resetSceneState()` invoked before rebuilding: clear every entity/history map, empty all object/UI arrays, null all GameObject handles, set `room` undefined, and reset clocks/latches/camera state. Also assign `carousel = []` before rebuilding.

3. **P1 — Remote-entity rendering allocates several objects per entity per frame.**  
   Refs: `packages/client/src/net/snapshots.ts:64-68`, `:87-115`; `packages/client/src/scenes/ArenaScene.ts:1475`, `:1542-1548`, `:1555-1577`, `:1877`, `:1951`, `:2596`, `:2609-2622`, `:3117-3163`.  
   **Why:** `SnapshotBuffer.sample()` returns a fresh `{x,y}`, previous positions are replaced with fresh objects, each `rig.animate()` receives a new object literal, and removal passes spread every key set into arrays. At 300 enemies this is roughly 900 short-lived objects per render frame—about 54,000/sec—before 20 Hz snapshot objects and projectile arrays. That is enough to cause recurring minor GC pauses.  
   **Fix:** store previous coordinates as scalar fields on the rig, use `sampleInto(out)` or scalar sampling, reuse one animation-input structure per rig, iterate Maps directly while deleting, and implement snapshot storage as a fixed circular numeric buffer instead of `push`/`shift`.

4. **P1 — Unconditional depth writes force a full scene display-list sort every frame.**  
   Refs: `packages/client/src/entities/SpriteRig.ts:258-260`; `packages/client/src/scenes/ArenaScene.ts:1634`, `:2881-2908`, `:3164`, `:4210`.  
   **Why:** Phaser 4.1 queues a depth sort whenever `setDepth` is called, even when the value is unchanged. All players/enemies call it each frame; belt mode writes depth again in `projectBelt`, and every carousel card also rewrites a stable depth. This guarantees sorting of the entire scene list—including static floor décor, UI, and transient VFX—at 60 fps.  
   **Fix:** skip unchanged depth values, remove the duplicate belt write, update carousel depth only when selection changes, and move y-sorted actors/POIs into a dedicated `Layer` so only the dynamic layer is sorted.

5. **P1 — Projectile representation creates heavy churn and blend-mode thrashing.**  
   Refs: `packages/client/src/scenes/ArenaScene.ts:1812-1836`, `:1877-1895`; `packages/client/src/scenes/arena/projectile-factory.ts:106-140`, `:163-222`.  
   **Why:** each projectile is a Container plus three to five separate Shape/Image objects, all destroyed on expiry. Child order frequently alternates ADD and NORMAL—for example additive trail → normal pellet/core, or additive trail → normal grenade shell → additive fuse. With hundreds of bullets, this repeatedly breaks blend batches while projectile turnover continuously allocates Containers, shapes, arrays, and tweens.  
   **Fix:** pool visuals per projectile kind and reduce common bullets to one atlas sprite. Put additive trails/glows in one shared additive layer or emitter and normal cores in a normal layer, grouped by blend mode rather than interleaved per Container.

6. **P1 — Horde-wide hits can allocate hundreds of GameObjects and canvas textures in one patch.**  
   Refs: `packages/client/src/scenes/ArenaScene.ts:3606-3647`, `:3753-3803`; `packages/client/src/scenes/arena/vfx.ts:558-620`; `packages/client/src/vfx/particles.ts:51-72`.  
   **Why:** every HP drop creates a Phaser Text, a painted-particle Image per particle, a core, four to six spark rectangles, and a tween for each. Phaser Text creation also allocates and uploads a canvas texture. An AoE hitting 100 enemies can create roughly 700–1,000 GameObjects/tweens in one server patch, followed by a similarly concentrated destruction/GC wave.  
   **Fix:** use persistent particle emitters with `explode`, pool or replace damage Text with BitmapText, impose a per-frame VFX budget, and aggregate or stagger off-screen/same-frame damage effects.

7. **P1 — The carousel renders and updates the whole arsenal, including off-screen cards.**  
   Refs: `packages/client/src/scenes/ArenaScene.ts:4145-4147`, `:4190-4251`; `packages/client/src/scenes/arena/card-art.ts:235-343`.  
   **Why:** all 21 current arsenal cards are built eagerly, remain visible, and have their transforms, depth, stat objects, formatting closure, text, and colors updated every frame. Moving a Container off-screen does not hide it; Phaser still traverses its many Text/Graphics/Image children. The cards also contain numerous unique Text and baked-card textures, producing substantial texture-binding and submission overhead.  
   **Fix:** instantiate or show only the selected card and two nearby neighbors, set all others invisible before the update loop, cache computed card stats, and refresh them only when weapon/attributes/loot change.

8. **P1 — Removed pickups leave immortal counter tweens running.**  
   Refs: `packages/client/src/scenes/ArenaScene.ts:878-879`, `:983-997`, `:1000-1004`.  
   **Why:** the spin uses `addCounter({ repeat: -1 })`. A counter tween targets an internal plain `{value}` object, not the pickup GameObject, so destroying the Container does not terminate it. Its closure permanently retains and updates the destroyed `img`, `glow`, and `shine`. Every collected or retro-upgraded pickup adds another 60 Hz callback for the rest of the scene session.  
   **Fix:** retain the Tween handle and destroy it when the pickup is removed, or drive pickup rotation from `time.now` in the existing sync/update pass.

9. **P1 — VFX surface reuse races active tweens and truncates/teleports particle tails.**  
   Refs: `packages/client/src/vfx/VfxPlayer.ts:203-227`, `:287-302`; `packages/client/src/vfx/vfx-render.js:714-742`, `:647-659`.  
   **Why:** when all 12 surfaces are busy, `acquire()` steals `pool[0]` without stopping its counter. The old counter can subsequently clear/hide/release the newly assigned effect. Even normal release happens at 470 ms while ember/scatter particles live for up to 780–880 ms; hiding and immediately reusing the parent Container cuts tails and can move surviving particles to the next strike point.  
   **Fix:** store the active tween and generation ID per surface, cancel/reset it before reuse, reject or round-robin-steal safely, kill remaining particles on steal, and keep a surface busy/visible until its maximum particle lifetime expires.

10. **P1 — Thrown Rusty Cleaver bypasses the packed atlas and requests an unloaded texture.**  
    Refs: `packages/client/src/scenes/arena/projectile-factory.ts:80-90`; `packages/client/src/scenes/ArenaScene.ts:480-510`; `packages/client/src/entities/SpriteRig.ts:14-24`.  
    **Why:** `makeThrownCleaver()` hard-codes `"rusty-cleaver:part-1"`, but normal weapon parts are loaded only inside `dd-sprites`; the loose texture is not preloaded. The default thrown weapon therefore renders as a missing texture despite its atlas frame existing.  
    **Fix:** resolve it through `partTexture(scene, "rusty-cleaver", part.role)` and pass both returned key and frame.

11. **P2 — Belt projectile tells mix projected and simulation-space Y coordinates.**  
    Refs: `packages/client/src/scenes/ArenaScene.ts:1403-1404`, `:3377-3387`, `:3397-3407`.  
    **Why:** `projectBelt()` runs first, so `c.y` is projected, but distance checks compare it with unprojected `PlayerState.y`. This makes the 150 px parry-tell threshold depend incorrectly on depth. The rift charge arc is also drawn at raw `st.riftY`, placing it away from the projected rift.  
    **Fix:** calculate threat distance entirely in world space using projectile/player state, then separately draw at `beltY(worldY)`. Project `riftY` before drawing the charge arc.

12. **P2 — DPR is captured once and becomes stale after monitor or browser-zoom changes.**  
    Refs: `packages/client/src/render-dpr.ts:12`; `packages/client/src/main.ts:20-22`, `:49-52`; `packages/client/src/scenes/ArenaScene.ts:649-655`, `:687-693`.  
    **Why:** changing `devicePixelRatio` later leaves buffer size, CSS zoom, camera zoom, and UI division using the startup value. Moving from 1× to 2× produces a soft undersized buffer; moving from 2× to 1× retains approximately four times the necessary pixel fill.  
    **Fix:** expose a mutable/current DPR calculation and react to DPR media-query changes as well as resize, atomically updating drawing-buffer size, ScaleManager CSS zoom, camera zoom/size, and HUD layout.

13. **P2 — Repeated rig flashes race one another and accumulate timers.**  
    Refs: `packages/client/src/entities/SpriteRig.ts:462-466`, `:484-486`.  
    **Why:** every hit schedules a new delayed `restTint()`. If another flash occurs first, the older timer clears the newer flash early. Destroyed rigs are also retained by pending timer closures until each timer fires. Rapid AoE hits can create many timers and visibly shorten flashes.  
    **Fix:** keep one `TimerEvent` per rig, cancel/reschedule it on `flash()`, and remove it in `destroy()`.

14. **P2 — Player-history maps are not pruned when a player leaves.**  
    Refs: `packages/client/src/scenes/ArenaScene.ts:199-202`, `:365`, `:1231-1239`, `:3143-3149`, `:3656-3659`.  
    **Why:** `lastParried`, `lastRevived`, and `lastFell` retain every departed session ID, while `removeBlob()` clears only some player maps. Long-running public rooms steadily retain join/leave history.  
    **Fix:** delete all three entries in `removeBlob()` and clear them during scene reset.

15. **P2 — HUD/debug code creates avoidable garbage and mutates the DOM at 60 Hz.**  
    Refs: `packages/client/src/scenes/ArenaScene.ts:3992`, `:4012-4018`, `:4032-4068`, `:4073-4125`, `:4746-4756`; `packages/client/src/net/prediction.ts:340-342`.  
    **Why:** several long strings, arrays, a Map, mapped augment parts, and predictor stats objects are recreated each frame. The always-present debug element receives `textContent` every frame, invalidating DOM layout even though most values change only at 1–20 Hz.  
    **Fix:** cache HUD signatures and update only on state changes; cache the augment summary; return predictor stats through scalar getters or a stable object; throttle the DOM debug readout to roughly 4–10 Hz.

16. **P2 — Card-art fallback also bypasses the atlas.**  
    Refs: `packages/client/src/scenes/arena/card-art.ts:58-98`; `packages/client/src/scenes/ArenaScene.ts:484`, `:503-510`.  
    **Why:** fallback art checks only `${id}:part-1`, but ordinary curated weapons are atlas frames. Current weapons without bespoke cards—Whirlwind, Arcane Lance, Storm Rod, and Hand Mortar—therefore receive the blank dark fallback despite installed sprite art.  
    **Fix:** resolve the atlas frame and draw its cropped source rectangle into the card canvas, falling back to the loose texture only for runtime-loaded expansion art.

17. **P2 — MenuScene also retains destroyed cards across re-entry.**  
    Refs: `packages/client/src/scenes/MenuScene.ts:33`, `:44-45`, `:93-95`, `:297-310`.  
    **Why:** `cards` is never cleared in `create()`. Re-entering the menu appends another card set while `layout()` still iterates destroyed roots, producing incorrect grid dimensions and retained references.  
    **Fix:** reset `cards`, optional object handles, and launch UI state at the start of `create()` or in a shutdown handler.

18. **P2 — Connection URL is hard-coded to insecure WebSocket.**  
    Ref: `packages/client/src/scenes/ArenaScene.ts:1165`.  
    **Why:** an HTTPS-hosted client will have `ws://` blocked as mixed content, so all 30 retries fail regardless of server health.  
    **Fix:** use a configured server URL, defaulting to `wss://` when `location.protocol === "https:"` and `ws://` otherwise.

# Report 2 — SERVER sim + netcode
1. **P0 — Production-reachable debug RPCs permit unbounded entity creation and process-wide denial of service.** The first joiner automatically becomes host ([GameRoom.ts:1384](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1384)), can enter training ([GameRoom.ts:825](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:825)), and then any client can issue unlimited `debugSpawn` requests of up to 30 enemies each ([GameRoom.ts:860](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:860)). `debugSpawnOne` has no total-enemy cap ([GameRoom.ts:3710](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:3710)). Host-only boss-spawn controls are likewise always registered ([GameRoom.ts:843](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:843)). **Why:** a single client can create hundreds or thousands of schema entities, immediately feeding the quadratic collision loop and reliable broadcasts; all rooms share the same Node event loop. **Fix:** compile/register these handlers only behind a server-side development flag plus authenticated admin capability; also enforce a room-wide hard entity cap and per-client token bucket.

2. **P1 — Enemy separation is an unconditional O(E²) all-pairs loop, twice per tick.** `resolveEnemyCollisions` materializes the whole enemy list, runs two relaxation passes, and calls `Math.hypot` for every pair ([GameRoom.ts:1295](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1295), [GameRoom.ts:1298](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1298), [GameRoom.ts:1303](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1303)). The current cap explicitly anticipates a future hundreds-per-player horde ([constants.ts:214](/C:/Users/Exped/DDv2/packages/shared/src/constants.ts:214)). **Why:** 500 enemies produce 249,500 pair tests per pass—about 10 million expensive pair tests/second at 20Hz before AI, projectiles, encoding, or four-player contact work. **Fix:** build a uniform-grid/spatial-hash broad phase once per tick and compare only entities in the same/adjacent cells; reuse that index for contact, melee, AoE, and projectile queries.

3. **P1 — Friendly projectile collision is O(P×E), with additional full-enemy scans for explosions and melee samples.** Every friendly projectile scans every enemy each tick ([GameRoom.ts:3413](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:3413)); every detonation scans the full horde ([GameRoom.ts:2913](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:2913)); swept melee can scan the horde multiple times per player per tick ([GameRoom.ts:2168](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:2168)). **Why:** four rapid-fire players with 150 live friendly shots and 500 enemies create 75,000 projectile/enemy tests per tick, or 1.5 million/second, before explosions and blade supersampling. **Fix:** query the same spatial index proposed above using each projectile’s swept segment/AABB and each melee/AoE footprint; test exact geometry only on returned candidates.

4. **P1 — The advertised arena-wide hostile-projectile ceiling is enforced only for boss payloads.** `BossController` applies the budget when a boss cast resolves ([BossController.ts:417](/C:/Users/Exped/DDv2/packages/server/src/rooms/BossController.ts:417)), but generic spitters call `fireProjectile` without checking it ([GameRoom.ts:2519](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:2519), [GameRoom.ts:2545](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:2545)). This contradicts the documented arena-wide hard ceiling ([constants.ts:418](/C:/Users/Exped/DDv2/packages/shared/src/constants.ts:418)). **Why:** a ranged swarm can exceed 120 hostile shots, multiplying both schema traffic and collision work at 20Hz; the boss merely stops adding its own shots after overload already exists. **Fix:** enforce admission centrally in `fireProjectile` with an O(1) hostile count, covering boss, spitter, and future sources; update the count on reflection and removal.

5. **P1 — Every moving enemy and projectile is full-schema synchronized to every client at 20Hz, with no AOI or lower-tier snapshot channel.** The schema itself notes that StateView/AOI is not wired ([state.ts:20](/C:/Users/Exped/DDv2/packages/shared/src/state.ts:20)); all enemies and projectiles live in global `MapSchema`s ([state.ts:246](/C:/Users/Exped/DDv2/packages/shared/src/state.ts:246)). Their positions change every tick ([GameRoom.ts:1787](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1787), [GameRoom.ts:3324](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:3324)), even though projectiles are already client-dead-reckoned from velocity ([ArenaScene.ts:1899](/C:/Users/Exped/DDv2/packages/client/src/scenes/ArenaScene.ts:1899)). **Why:** hundreds of bodies plus bullets generate thousands of changed numeric fields per patch, replicated four times over reliable WebSockets; backlog causes head-of-line latency for input acknowledgements and telegraphs. **Fix:** retain schema sync for lifecycle/static data and Tier-1 entities, but send packed, quantized position snapshots at a lower cadence with per-client AOI. For straight projectiles, sync spawn/velocity/despawn plus occasional correction rather than x/y every tick.

6. **P1 — Defeated rooms keep running the complete horde simulation and broadcasting forever.** Defeat only changes `state.outcome` ([GameRoom.ts:1945](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1945)); subsequent ticks still execute AI, projectiles, collisions, and contact, while `update` continues broadcasting every stepped batch ([GameRoom.ts:1454](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1454), [GameRoom.ts:1782](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1782)). Victory cleanup also omits zones and several transient collections ([GameRoom.ts:3749](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:3749), [GameRoom.ts:4026](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:4026)). **Why:** a wiped four-player room retains its maximum-cost O(E²) swarm and 20Hz network stream while players sit on the defeat screen; leftover victory zones continue ticking and can damage players after the run ends. **Fix:** on terminal outcome, clear all combat entities and `clearTransients`, then short-circuit `stepSim` to minimal input/restart handling or move the terminal room to a low-frequency timer.

7. **P1 — Belt meta-progression is client-authored at join.** `scrip` and upgrade ownership come directly from room options, are merely clamped, and are immediately applied to authoritative stats ([GameRoom.ts:1348](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1348), [GameRoom.ts:1358](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1358), [GameRoom.ts:1361](/C:/Users/Exped/DDv2/packages/server/src/rooms/GameRoom.ts:1361)). Sanitization bounds levels but does not prove ownership ([meta.ts:41](/C:/Users/Exped/DDv2/packages/shared/src/meta.ts:41)). **Why:** any of four clients can join with 65,535 scrip and all upgrades, gaining HP, damage, luck, and economy advantages without earning them. **Fix:** identify players through an authenticated account/session and load progression from server-owned storage; ignore progression fields in client join options.

8. **P1 — Vertical reconciliation can cancel an unacknowledged locally predicted jump.** A local jump is immediately integrated and placed in `pending` ([prediction.ts:176](/C:/Users/Exped/DDv2/packages/client/src/net/prediction.ts:176)), but reconciliation replays pending commands only horizontally ([prediction.ts:258](/C:/Users/Exped/DDv2/packages/client/src/net/prediction.ts:258)). It then overwrites vertical state whenever divergence exceeds 12px ([prediction.ts:271](/C:/Users/Exped/DDv2/packages/client/src/net/prediction.ts:271)). With `303px/s × 0.05s`, the first predicted jump step is 15.15px, already over that threshold. **Why:** if a patch representing the pre-jump server tick arrives before the jump command is acknowledged—a normal 20Hz/RTT ordering—the client adopts height 0 and loses the instant hop until later server truth arrives. **Fix:** include authoritative jump cooldown/buffer state in the rebase and replay vertical physics for pending commands, or introduce an acknowledged jump-action sequence and never adopt pre-action height while that jump remains pending.
