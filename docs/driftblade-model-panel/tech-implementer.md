## 1. Routing layer — explicit adopter map in melee.ts (weapons-tag flag rejected)

**Decision: an explicit adopter table in `melee.ts`, at the exact seam `bigSwordPanelVariantFor` already
occupies. The weapons-tag route (`def.comboVariant`) is rejected for this wave.**

Evaluation:

| | `comboVariant` tag in weapon data | explicit map in melee.ts |
|---|---|---|
| 4 of 5 adopters live in `weapons-expansion.generated.ts` | requires hand-editing a DO-NOT-EDIT generated file, or a `data/weapon-concepts-300.json` + generator change — both outside this wave's file locks and clobbered on regen | zero generated-file edits |
| file locks | `weapons.ts` is not in the lock set | `melee.ts` is |
| precedent | none — no weapon authors `comboFamily`/`comboVariant` today (grep: zero data occurrences; the fields exist only as the module-augmentation seam) | `bigSwordPanelVariantFor` is exactly this, self-documented as "the non-generated rollout table permitted by the panel" |
| non-adopter safety | tag precedence (`def.comboVariant` wins at L935) means a stray regenerated tag re-routes silently | the map is consulted at one audited call site |

Shape of the change (all inside `meleeComboSelectionFor`'s existing flow):

```ts
/** Driftblade-model rollout table (panel §50+). Non-generated ids only, same law as bigSwordPanelVariantFor. */
export const DRIFT_MODEL_ADOPTERS = Object.freeze({
  "x2-gravechill-nodachi": "nodachi-gravechill",
  "x2-stormpetal-odachi": "nodachi-stormpetal",
  "x2-hailwidow-katana": "tachi-drift",
  "x2-voltfang-tachi": "tachi-drift",
} as const satisfies Record<string, SignatureMeleeComboVariant>);
```

- Consult it **inside `bigSwordPanelVariantFor`** (or immediately before it at L968) — i.e. *before* the
  quake-mauler heuristic. Order is load-bearing: if gravechill is removed from the `"greatsword"` case
  without being matched first, it falls through to `def.twoHanded && def.quake && size XL → "quake-mauler"`
  (L970) and silently becomes a maul.
- `driftblade` itself **stays on `"greatsword"`** — it is the model, and the bigsword test's "nodachi
  benchmark" block pins it there. The adopter map covers only the four followers.
- Non-adopter byte-identical invariant, stated explicitly: **for every weapon id not in
  `DRIFT_MODEL_ADOPTERS`, `meleeComboSelectionFor(def, style)` must return a result deep-equal to today's,
  produced by the identical code path** — the map lookup returns `undefined` for them and every line
  after it is untouched. That covers the four shipped rosters (momentum/breach/glaive/bardiche cases in
  the same switch), `quake-mauler`/`stinger`/`hero-spin`/`pommel` heuristics, the close-blade lanes, and
  the `undefined` holes (whirlwind, anchor, buzzsaw, spade). §7's table test makes this machine-checked.

## 2. Template vs copy — composed frozen step consts (the existing pattern), no runtime builder

**Verdict: shared template = shared frozen *step constants* composed into per-adopter arrays — exactly the
mechanism `MELEE_COMBO_VARIANT_SEQUENCES` already uses (`requiredBaseComboStep("chop", 0)` reused across
`quake-mauler`/`pommel`/`greatsword`). Where an adopter's beat differs from the model, it gets its own
explicit `as const satisfies MeleeComboStep` constant. No factory/builder function, no literal reuse of
the whole `greatsword` array.**

Why not a parameterized builder (`driftStep(base, overrides)`) even though it's type-sound:

- **Remote determinism** is trivially guaranteed by static data: owner prediction and remote observation
  both resolve `weaponId → variant → frozen array → comboStepForChain(attackSeq…) → step index`. Every
  input is either immutable module data or the synced accepted beat. A builder evaluated at module load is
  equally deterministic — but a builder invoked at *selection time* (to fold in weapon stats) would
  allocate per swing and open an owner/remote divergence surface for zero gain. If parameterization by
  weapon is ever wanted at runtime, it belongs in the *renderer* (which already has `meta.reach`/`meta.size`),
  not in the step tables.
- **The as-const literal law** (melee.ts L435 comment): union-typed fields (`motion`, `direction`, `hand`,
  `path.kind`, `ribbon.profile`, `ribbon.end`) in exported shared tables widen to `string`/`number`
  without `as const`, and the shared package's declaration build (`tsc`) fails. The existing pattern —
  `Object.freeze({ … } as const satisfies MeleeComboStep)` — satisfies it mechanically and keeps every
  authored number greppable/reviewable. A builder hides the effective numbers from both review and the
  declaration check.
- **Maintainability**: the "model" is enforced as *bands over the tables* by the §7 test (the analyst's
  M1–M8), not as a shared array. That is the honest reading of "like-combos, not literal reuse": adopters
  may share an individual beat constant where the designer wants an identical beat (the composition
  pattern), must differ elsewhere, and the test — not a pointer — proves conformance.

Concretely per the analyst's tiers: the two nodachi de-clones get three bespoke step consts each
(new motions, §5 Tier 2); the two fast tachi share one `tachi-drift` variant whose steps reuse the model's
*grammar* at phrase level (cadence gate: no tremor/deformation sub-beats) — these can be authored reusing
existing motions (`shoulder-chop` opener root + specialized PUNCTUATE/PAYOFF consts) to stay Tier 1.

## 3. Step-schema audit — what exists vs what's new

Already expressive enough (no schema change):

- `timing` (activeStart/activeEnd/impact/followEnd + secondary pair) — covers every model beat including
  the TCS-style long anticipation; fractions are cadence-normalized, so the katana's 0.30 s pose reuses
  the same numbers under the analyst's phrase-level gate.
- `path` — Stage-1 law: every new step ships the unit sweep (`kind:"sweep", arcMultiplier:1,
  rangeMultiplier:1, damageMultiplier:1, knockback:0`), same as all sixteen shipped panel steps; the
  authored non-unit values on the model's own steps predate the panel law and stay untouched.
- `ribbon` (`MeleeComboRibbon`) — profile/radialStart/radialEnd/widthMultiplier/end/setupEcho is already
  sufficient for the PER parameterization in §4. **No new step fields required.**

Union extensions required (each is a literal-law hazard — `as const` on every use):

- `MeleeComboVariant`: + `"nodachi-gravechill" | "nodachi-stormpetal" | "tachi-drift"` (names final per
  designer). `SignatureMeleeComboVariant` picks them up automatically; the
  `Record<SignatureMeleeComboVariant, …>` type on `MELEE_COMBO_VARIANT_SEQUENCES` then **fails tsc until
  the sequences exist** — this is the safety net, add the union member and the table in one edit.
- `familyForSignatureVariant`: **zero edit needed** — its default branch returns `"chop"`, which is
  correct for all three new variants. (The analyst's R4-1 warning applies only to a future non-chop
  variant; note it in a comment, don't restructure.)
- `MeleeComboMotion`: + up to 6 new motion literals (Tier 2 nodachi verbs only; `tachi-drift` reuses
  existing motions). Every new motion needs a SpriteRig dispatch branch or it silently falls into the
  generic family branch (`poseStyle === "chop"`) — acceptable fallback, but flag it in review.
- `MeleeComboRibbonProfile`/`MeleeComboRibbonEnd`: extend only if the designer's ribbons don't fit the 12
  shipped profiles. Prefer reusing profiles: the §4 consumer keys off the *fields*, not the profile name,
  so new names are documentation, not behavior.

## 4. PER parameterization keyed to blade length/weight — where the data comes from

**No new plumbing for weapon geometry is needed.** `VfxPlayer.playSwing` already computes
`meta.reach = meleeReach(weapon)` (weapons.ts L333 — `max(range, (1−gripFrac)×displayLength)`, i.e.
Driftblade 304, gravechill ≈313, stormpetal ≈318, hailwidow ≈122), plus `meta.size` (`XL`→ 38 px body cap
in `PER_SIZE`, `M`→ 22 px), `meta.grip`, `meta.family`. `displayLength` is therefore already in the
renderer, pre-folded into reach; do not add a raw `displayLength` field to `per` meta (that would touch
`VfxPlayer.ts`, which this wave otherwise leaves at zero edits).

The per-*step* signal is `meta.swing.comboRibbon`, which arrives free on any enriched descriptor. The
`renderPer`/`samplePerClock` delta (all inside `vfx-render.js`):

- `const ribbon = meta.swing?.comboRibbon;` — absence must render **byte-identically to today** (guard
  every use; non-adopters and all legacy callers pass descriptors without the field).
- Radial band: inner radius = `frame.reach * ribbon.radialStart` (outer stays `frame.reach`;
  `radialEnd === 1` is test-asserted). Implemented as a band offset in `updateArcRope`'s radius/width
  inputs — the long-thin-nodachi look is a high `radialStart` (0.66–0.72, the glaive/bardiche precedent)
  driving a narrow outer crescent, which *scales with blade length automatically* because it multiplies
  reach.
- Width: `frame.bodyWidth *= ribbon.widthMultiplier`, still clamped by the existing
  `Math.min(42, size.body, …)` — the alpha/width budget caps are ceilings the ribbon cannot exceed
  (analyst R5 guardrail).
- `end`: head treatment only — `clean` (today's), `squared` (no tip taper), `torn`/`hooked`/`open`
  (alpha-notch/curl on the final rope segments). Keep it to vertex alpha/width writes in the existing
  point loop; no new display objects.
- `setupEcho: "neutral-dim"`: one extra `updateArcRope` pass at ≤0.22 alpha on the already-allocated
  `S.perLip` rope *before* the active window, or skip in Phase A — echo is optional per schema.
- **Both paths**: `drawPerFallback` (canvas/quality-4) must honor `radialStart`/`widthMultiplier` too —
  the fallback is exercised under pool pressure (`perQuality 4` at ≥10 live surfaces) and in preview hosts.
- Alpha law unchanged: `bodyAlpha ≤ 0.78`, one business edge, history caps intact. The ribbon consumer
  reshapes geometry; it adds no brightness.

**Owner-side descriptor plumbing** (the asymmetry in Ground Truth): add a public getter on SpriteRig
(`get activeSwing(): SwingDescriptor | undefined { return this.swing; }`) and change ArenaScene's two
local `spawnSlash` call sites (L6531/6540) to pass `rig?.activeSwing ?? swing` — `triggerSwing` (L6420)
runs before `spawnSlash` in the same `sendAttack` frame, so the enriched descriptor is already retained.
ArenaScene is **not** in the four-file lock nor owned by the server wave; see §8 for how it's handled.

## 5. SpriteRig changes

- **Tier 1 (`tachi-drift`, reused motions): zero pose-code edits.** Motion-keyed dispatch already routes

  timing fractions from any step. New variant literals flow through untyped locals (`poseVariant` is

- **Tier 2 (nodachi de-clone verbs): one dispatch `else if` per motion trio + two `applyXxxCombo` methods**
  (`applyGravechillCombo`, `applyStormpetalCombo`), modeled on `applyMomentumCombo` (L2460). Placement
  rule from the test's source-slice assertion (§6): new methods go **after** the
  `/** Hammer-head fulcrum vault` marker (L3091) *or* obey the no-`this.root.x/y`-writes invariant if
  placed inside the [`applyMomentumCombo` … fulcrum-vault) slice. Convention regardless of placement:

  `weaponLengthScale`, `attackHandSpacing`, `attackWeaponDepth` — never `this.root.*`.

  `"greatsword"`. Move it to `"nodachi-gravechill"` without extending this list and its visible contact
  desynchronizes from `swing.impactSeconds` — the quake detonates on the wrong pose frame.
  (Stormpetal has no quake; the `def.quake &&` guard makes its entry inert but future-safe.)
- **Optional (§4 owner plumbing): the `activeSwing` getter** — 3 lines, no state change.
- Nothing else: `triggerSwing`'s chain snapshot, `comboStepForChain` call, `comboHoldPose`,
  hit-stop mapping (`presentationEpochForWallEpoch`), and `flushObservedAttackSignature` are all
  variant-agnostic and untouched.

## 7. Table-driven test plan — "follows the model iff …" over the adopter mapping

New file `tests/driftblade-model-panel.test.ts`, driven entirely by the exported `DRIFT_MODEL_ADOPTERS`
so a future adopter (one map row + one sequence) auto-extends every check:

1. **Routing:** for each `[id, variant]` of `Object.entries(DRIFT_MODEL_ADOPTERS)`:
   `meleeComboSelectionFor(WEAPONS[id])` → `{family:"chop", variant}`; plus the anchor row
   `driftblade → "greatsword"`.
2. **Model conformance (analyst M1–M4/M7, encoded as bands over the tables):** for each adopter variant's
   sequence — 3 frozen steps, 3 distinct motions; anticipation ramp `A2 ≤ 0.6·A1`, `A3 ≥ 1.7·A1`
   (waived to the phrase-level subset for `tachi-drift` via a per-variant `cadenceGate` flag in the test
   table — cooldown ≤ 0.5 s read straight from `WEAPONS[id].cooldown`); PAYOFF `impact ≥ 0.58` and
   `followEnd ≥ 0.78`; timing monotonicity + impact-within-active (the shipped law, verbatim from
   bigsword L105–109).
3. **Stage-1 path law:** every adopter step `path` deep-equals the unit sweep (bigsword L98–104 applied
   to the new variants).
4. **Ribbon law:** every adopter step authors a ribbon; `radialEnd === 1`; `radialStart ≥ 0.6` for the XL
   nodachi (long-cutter band); `setupEcho` ∈ {undefined, "neutral-dim"}; at most one non-echo ribbon per
   step (the no-second-bright-contact rule).
5. **Not-a-clone (M8):** each adopter sequence differs from `MELEE_COMBO_VARIANT_SEQUENCES.greatsword` in
   ≥ 2 of {step-2 motion, step-3 motion, any timing value, any ribbon field}, and no adopter array is
   reference-equal to the greatsword array.
6. **Non-adopter invariance table:** build `actual = Object.fromEntries(ids.filter(hasSelection).map(id =>
   [id, `${sel.family}/${sel.variant}`]))` over **all** `Object.keys(WEAPONS)` and deep-equal it against
   an explicit literal expected-map (~20 rows: the four shipped rosters, the heuristic families, the
   adopters, the anchor). Any future routing drift — adopter or not — must edit exactly one visible row.
7. **Chain determinism:** for one adopter, `comboStepForChain` over three contiguous accepted beats within
   cadence → `0,1,2`, and a beat after `previousExpiresAtMs` → `0` (the rig-correctness pattern, run
   against adopter sequence length).
8. **Renderer guard (Phase B only):** source-string assertions on `vfx-render.js` — contains
   `comboRibbon` reads in both `renderPer` and `drawPerFallback` (fallback parity), following the repo's
   established source-assertion idiom.

Updates to existing files: the bigsword L78–84 split (§6). Nothing in `rig-correctness-panel.test.ts`
changes.
