## The defect
Account state, exact weapon escrow, disconnected reservations, settlement receipts, pet state, and
"already settled" markers are all process-local maps/sets (`packages/server/src/rooms/GameRoom.ts`
~574-589). The server package has only Colyseus/runtime deps — there is NO datastore at all. The room
mutates memory, marks the account settled, sends messages, and then relies on the BROWSER to write
`localStorage`.

Consequence: a server crash, room crash, deploy, restart, a throw mid-settlement, socket loss during
receipt delivery, or a blocked local write loses the result. Worse, `room-progression.ts` ~3060-3069
deliberately settles a still-open expedition as DEFEAT on a later join, because the old settlement
lived only in the old room — so a crash after legitimate extraction converts banked victory loot into
a loss.

**This directly violates a LOCKED design promise.** `docs/sol-reports/design-lock-b20.md` states money
banks 100% at run end. Today it does not.

## Build it
1. **Durable store: SQLite with WAL.** Single-node solo-dev deployment; do not introduce a server or
   network dependency. Add it to `packages/server` only.
2. **Schema**: account snapshots and settlements. **Unique constraint on `(account_id, run_id)`** —
   this is the idempotency key and the whole correctness argument.
3. **Commit BEFORE acknowledging.** Outcome + account changes must be durably committed under the
   idempotency key before the server tells the player they won. Never the other way round.
4. **On reconnect or new join, return the COMMITTED receipt/account from storage.** Never infer defeat
   from a stale client blob when a committed terminal record exists. This is the specific line that
   currently turns wins into losses — fix it, do not preserve it.
5. Re-running the same `runId` must produce ONE identical receipt and balance. Idempotent, not additive.
